- B2B prospecting lives in staff-only `prospects` with rules in browser-safe `src/lib/prospection.ts`; mails open in the user's own mail client (mailto), never via app emails, to protect invoice/quote deliverability and French opt-out rules. Send state (sent/to-confirm/relance due) and same-contact duplicate/STOP blocking come only from `prospection.ts` helpers, so a company is never contacted twice by mistake.
- Sorank blog: articles live in `blog_articles`, audit fixes in `seo_page_overrides` (+ history) applied at render via `src/lib/sorank/rendu.ts`; the public webhook logic in `src/lib/sorank/webhook.ts` stays storage-agnostic and coded pages accept only title/description/JSON-LD fixes (why: SSR pages, safe retries, revertable fixes without rewriting coded content).
- The chantier pipeline (1 done without attachment, 2 attachment to send, 3 sent not opened, 4 opened awaiting order, 5 order in/to invoice, 6 invoiced/to receive, 7 received/to deposit, 8 done) comes only from browser-safe `src/lib/etape-chantier.ts`, read by `getSuiviChantiers` (one row per chantier share of an attachment; a TS only ever shows its own order, never the initial attachment's) and shown grouped by contractor on `/suivi` + dashboard; reception is offered only once an order exists and nothing changes billing state. Recording an order number uses `enregistrerCommandeAttachement`, which never invoices. A separate "all received" view/total (`totalReceptionnes`) lists every received chantier whatever its step, counting only documents with their own order (`ligneReceptionnee`), so TS or duplicate invoices awaiting an order never inflate the received bundle. `bilan-reception.functions.ts` remains only for the emailed report.
- A chantier belongs to one ordinary (non-TS) attachment: creating/editing an attachment is refused when its chantiers are already in another sent/accepted/invoiced one, and invoicing is refused when another ordinary attachment of the same chantier is already invoiced; supplements go through TS (why: prevent double billing; drafts stay redoable).
- Suivi groups contractors by `nomDonneur` (case, accents, punctuation and legal form ignored) and flags received chantiers without any order via `receptionnesSansCommande`, at chantier level (why: one client per company and a per-chantier order rule, without editing records).
- Import parsing (`import-chantier-local.ts`) strips the technical visitor's lines before reading the client, rejects sentence-like names, and stores only extracted values plus explicit remarks in notes/resume, never the whole document (the original file stays attached). Planning import hides chantiers already in the planning (kept in a collapsed "import anyway" list), and the fiche dialog offers only open chantiers via `chantiersAFicher` (why: no re-selection of existing chantiers, no client/technician confusion).
- Devis, attachement and invoice lists share one search rule in browser-safe `src/lib/recherche-periode.ts` (Monday–Sunday weeks, months, manual dates, accent-insensitive text, by issue date) rendered by `RechercheDocuments` (why: same period logic everywhere; filtering never changes documents).
- Attachment send state (not sent → sent/awaiting validation → validated → invoiced) comes only from browser-safe `src/lib/attachement-envoi.ts`, and lists title attachments with resident names via `nomsAttachement` (linked chantiers first), never a bare "brouillon"/number (why: one readable send circuit, names always visible).
- Platform deposit bundles (`BlocDossiersPlateforme` on Bons de commande, rules in `bloc-dossiers.ts`) zip invoice + order (signed if present) + attachment per order, one folder per invoice, ASCII folder names; selection defaults to received chantiers or pasted order numbers and never changes any state.
- Attachment lines carry their chantier: the editor offers a per-line chantier choice (terminated, not yet attached chantiers via `listChantiersAAttacher({ tous: true })`) and inserted lines inherit the chantier of the line above; Suivi flags attachments with unlinked lines (why: an unlinked line leaves its chantier at step 1).
- Attachment duplicates come only from browser-safe `src/lib/doublons-attachement.ts` (same contractor + shared chantier, or identical week/lines/total when one has an unlinked line; TS and cancelled never compared): `createAttachement` returns the matches instead of creating until the user confirms (`confirmer_doublon`), and the Attachements page lists possible duplicates where only never-sent, uninvoiced drafts can be deleted after confirmation (why: avoid double billing without ever deleting automatically).
- Client reminders from Suivi (`envoyerRappelClient`) recompute steps server-side via shared `chargerSuivi` and browser-safe `src/lib/rappel-client.ts` (steps 3-4 = order awaited, 6 = reception awaited), derive the recipient from the attachments, and only update `rappel_at`/`nb_rappels` (why: never trust the browser, never change billing state).
- Site-wide duplicates (chantiers, invoices, quotes, partner and billing-client records) come only from browser-safe `src/lib/doublons-site.ts`, listed by `listDoublonsSite` on `/doublons` (plus `BandeauDoublons` on each list page) and acted on by `traiterDoublon`, which re-checks the pair server-side: chantiers/quotes are deleted only when nothing is linked, issued invoices are cancelled never erased (paid ones untouched), different order numbers or TS invoices are never duplicates, and records are merged before deletion (why: clean data without losing documents or breaking invoice numbering).
- Suivi PDF bundles (`TelechargerPdfSuivi`) zip, for the checked rows (or the whole step), one folder per invoice or unbilled attachment with invoice PDF (text), attachment PDF and the stored order (signed if present); read-only (why: download any step for client platforms without changing state).
- An order number is used once: `commandeDejaUtilisee` (attachements.functions) refuses it on any other attachment (TS included), invoice or imported order when creating/editing an attachment or TS, recording an order, or invoicing (why: a TS is billed separately and waits for its own order; reusing an order loses money).
